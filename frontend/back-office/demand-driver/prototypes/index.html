Research notes. The current "Replace [item]" sections are a bare <input type="file"> plus a button - functional but visually flat next to the rest of the console. Five patterns below come from how file-replace flows are actually built elsewhere: dual drag-and-drop + click-to-browse as the baseline expectation; keeping (not silently discarding) the previous version, per the same source; the hover-to-reveal-edit pattern Adobe Portfolio and most cover-image editors use; Google Drive's "manage versions" and Figma's version history as the model for version-aware replacement; and dashboard-card guidance on an 8px spacing unit and letting type/space (not boxes) carry hierarchy, from card/spacing best practices.
Prototype 1 of 5 · Dropzone. The baseline expected pattern: a large drag-and-drop target with a click-to-browse fallback button, so both mouse-drag and keyboard/screen-reader users have an obvious path in.

Prototype 3 of 5 · Compact File Row. The lowest-chrome option: each item is one dense row (icon, filename, metadata, inline actions) instead of a full card. The Replace action is a real, keyboard-accessible file input visually hidden behind a styled label - the accessible pattern for file inputs. Best when a page has many such rows and can't afford a full card each.

Prototype 4 of 5 · Version-Aware Upload. Borrows the Google Drive / Figma model: replacing a file creates a new version rather than silently overwriting the old one, and that history is one click away. Best fit for the T&Cs specifically, since a demand driver may need to point back to what an applicant actually agreed to.

Prototype 5 of 5 · Minimal Inline Swap. The lightest-weight option, with no card chrome at all - just a labeled value and a text-link action, the way Notion or Airtable treat an attachment field. Hierarchy comes from type and spacing, not boxes, matching the admin-dashboard guidance that boxes-on-boxes is what makes a console feel bland in the first place.
